The Odoo Developer

The engineer who turns specifications into working software. The Odoo Developer takes the Functional Consultant's functional spec and the Solutions Architect's technical design and produces what neither a setting nor Studio can deliver: reliable custom code. If the FC owns fit and the SA owns the technical design, the Developer owns execution — building functionality that does exactly what was specified, performs well, and, above all, survives the next Odoo upgrade. Their deliverable is not a clever module; it is custom functionality that keeps working long after they have moved on.

Module 1

What the role really is

An Odoo Developer is the person who writes the code that standard Odoo, configuration, and Studio cannot produce. By the time work reaches the Developer, the requirement has already been filtered hard: the Business Analyst captured the need, the Functional Consultant decided it was a genuine gap configuration couldn't close, and the Solutions Architect designed how it should be built. The Developer answers the last question in the chain: "How is this implemented in clean, correct, maintainable Python and XML — exactly as designed?"

The Developer's product is working, maintainable custom functionality. Not a configured database (that is the FC), not an architecture diagram (that is the SA), and not a requirements document (that is the BA) — but running code: a custom field that computes correctly, a wizard that posts the right journal entries, a report that prints, an integration that syncs without falling over at 2 a.m. Everything the Developer does ladders up to functionality that behaves as specified and keeps behaving as Odoo evolves.

On an Odoo implementation the Developer sits at the end of the build chain, bridging three things:

  • The functional spec — the FC's precise statement of what the feature must do, in business terms, with acceptance criteria.
  • The technical design — the SA's decisions on which models to extend, how data flows, where integrations sit, and the conventions to follow so the system stays coherent and upgradeable.
  • The Odoo framework — the ORM, the view system, the security model, the addon architecture. The Developer knows the framework's grain better than anyone and works with it, never against it.
The mark of a senior Odoo Developer is not the cleverness of what they build but the boredom of it: code that reads like the rest of Odoo, extends rather than overrides, is covered by tests, and that the next developer — or the SA on an upgrade two years out — can understand and trust at a glance.
Definition

An Odoo Developer implements custom functionality in the Odoo framework — Python business logic, the ORM, XML views, QWeb reports, OWL front-end, controllers, security — building it as clean, tested, upgrade-safe extensions that realise the Functional Consultant's spec within the Solutions Architect's design. Their deliverable is reliable custom code that survives upgrades.

Module 2

The developer's mindset

Before the framework details, the operating instincts. Strong Odoo developers think in a recognisable way — and most of it is about restraint and the long term, not raw output:

Upgrade-safety first

Every line is written to survive the next major Odoo release. The developer extends through inheritance, never edits core, and treats "will this still work after the upgrade?" as the first question, not the last. Code that traps a client on an old version is a failure no matter how well it works today.

Follow Odoo conventions

The framework has a grain — naming, structure, ORM idioms, view patterns. The developer writes code that looks like the rest of Odoo, so anyone fluent in the framework can read it. Convention is not constraint; it is what makes the codebase legible and maintainable.

Simplicity over cleverness

The best solution is the simplest one that meets the spec. Clever code impresses for a week and confuses for years. The developer optimises for the person who reads the code next, not for their own ego today.

Test what you build

Code without tests is a liability waiting for UAT to find it. The developer writes automated tests from the acceptance criteria, covers the edge cases, and treats "it works on my machine" as not done.

Communicate effort & blockers

An honest estimate and an early flag are worth more than heroics. The developer surfaces complexity, effort, and blockers the day they appear, so the PM can plan and the FC doesn't over-promise in a demo.

Reuse before rebuild

Before writing anything, the developer asks whether Odoo, the OCA, or TechNext's own catalog already solves it. The cheapest, most maintainable module is the one you didn't write — reuse first, build only the genuinely new.

Module 4

The Odoo tech stack a developer must know

Odoo is a full-stack framework, not just a database with screens. A productive Odoo developer is fluent across the whole stack — Python on the server, the ORM in between, XML and JavaScript on the client. Below is the surface area the role demands.

LayerWhat it isWhat the developer must know
Python & the ORMThe server language and Odoo's Object-Relational Mapping layer over PostgreSQL.Recordsets, self as a recordset, search/browse/read, create/write/unlink, env, @api decorators, batching — never raw SQL unless justified.
Models & fieldsThe data definition layer: Python classes mapping to database tables.Char, Text, Integer, Float, Boolean, Date, Datetime, Selection, Many2one, One2many, Many2many; compute/related/store fields with @api.depends; SQL and Python constraints.
XML viewsThe declarative UI definition: how records are displayed and edited.Form, tree/list, search, kanban, pivot, graph, calendar views; actions, menus, and the view inheritance mechanism (xpath).
QWeb reportsOdoo's templating engine for printable PDF documents.QWeb templates, report actions, paper formats, translatable layouts, computing report data.
OWL / JavaScriptOdoo's modern front-end framework (Odoo Web Library) for interactive UI.Components, hooks, the registry, custom widgets, client actions, patching existing components — when the UI must go beyond standard views.
Controllers (HTTP/JSON)The web layer for endpoints — portal pages, webhooks, REST/JSON APIs.http.Controller, @http.route, type='json' vs 'http', auth modes, CSRF, returning responses safely.
SecurityWho can do what, and which records they can see.ir.model.access.csv (CRUD per group), record rules (ir.rule) for row-level access, security groups, field-level access — security by default, not as an afterthought.
Data & demo XMLSeed and configuration records loaded with the module.noupdate data, external IDs (XML IDs), demo data, sequences, default records — and the load order in the manifest.
The manifest__manifest__.py — the module's declaration.Name, version, depends, data (the ordered list of XML/CSV files), assets, license, installable/application — the spine that tells Odoo what to load and in what order.
ℹ️ Why breadth matters

A single small feature can touch every layer: a new Many2one field (model), shown on a form (view), validated by a constraint (Python), printed on an invoice (QWeb), guarded by access rights (security), and seeded with a default record (data XML). The developer who only knows Python writes half a feature; the one who knows the whole stack ships the whole thing.

Module 5

Anatomy of a custom module

Everything a developer builds in Odoo lives in an addon module — a self-contained folder that Odoo can install, upgrade, and uninstall as a unit. Knowing the standard structure cold is the foundation of the craft, because Odoo loads a module by convention, not configuration.

The standard directory structure

  • __manifest__.py — the module declaration: name, version, dependencies, the ordered list of data files to load, assets, and license.
  • __init__.py — Python package init; imports the models, wizard, controllers subpackages.
  • models/ — Python model definitions: new models and inheritance of existing ones, with their fields, compute methods, constraints, and business logic.
  • views/ — XML for forms, lists, search views, kanban, actions, and menus, plus view-inheritance records.
  • security/ — ir.model.access.csv (access rights per group) and XML for security groups and record rules.
  • data/ — XML/CSV seed data: sequences, default records, email templates, scheduled actions, configuration loaded with the module.
  • static/ — front-end assets: static/src/js (OWL components), static/src/scss (styles), static/src/xml (OWL templates), and images/description.
  • wizard/ — transient models (TransientModel) and their views: the pop-up dialogs for multi-step user actions.
  • report/ — QWeb report templates, report actions, paper formats, and any report-specific Python.
  • tests/ — automated tests (TransactionCase, HttpCase), run on every push in CI.
  • i18n/ — translation files (.po / .pot) for multilingual deployments.

How it loads

When Odoo installs or upgrades the module, it reads __manifest__.py, resolves and loads the depends modules first, imports the Python (registering models in the ORM), then loads each file in the data list in the exact order written — security before views that reference groups, data before views that reference it. Get the order wrong and the upgrade fails. The manifest is therefore not boilerplate; it is the load script for the whole module.

💡 Scaffold, then shape

Odoo ships a scaffold command that generates this skeleton for you. Start from it — never hand-roll directory names — so the structure is correct and conventional from the first commit. The discipline is keeping the structure clean as the module grows: models in models/, one concern per file, and a manifest whose data list reads like a sane load order.

Module 6

Inheritance & upgrade-safe development

This is the single most important technical habit in the whole role. Odoo is built to be extended without being modified, and the entire upgradeability of a client's system rests on developers using that mechanism instead of editing core. There are three forms of inheritance, and a developer must know exactly when to reach for each.

_inherit — extension

The workhorse. Reopen an existing model to add fields, override or extend methods, and add constraints — without touching the original code. The model keeps its table; you are layering behaviour onto it. This is how the vast majority of customizations should be built.

_inherits — delegation

Delegation inheritance: your new model embeds another model by reference (a Many2one) and exposes its fields as if they were its own. Used where one record genuinely is-a another plus extra data — the classic example being how a product variant delegates to its template.

View inheritance — xpath

To change a screen, you don't replace the view — you inherit it and surgically insert, replace, or move elements with xpath expressions (e.g. add a field after an existing one). The original view stays intact; your changes layer on top and can be applied or removed cleanly.

Overriding methods with super()

When you extend a method, you call super() to run Odoo's original logic and then add yours around it. This preserves standard behaviour — and every other module's extensions of the same method — instead of silently discarding them. Forgetting super() is a classic source of subtle breakage.

The golden rule that ties all of this together: never edit Odoo core. Every customization is an addon that layers on top through these mechanisms. Done this way, an upgrade is a matter of re-testing your addons against the new version; done the other way, an upgrade is a rewrite — or impossible.

⚠️ Core overrides and hacks break upgradeability

The moment a developer edits an Odoo core file, copies a core file to "tweak" it, or hacks around the framework instead of extending it, the client's path to the next Odoo version is broken. Those changes vanish or conflict on upgrade, security patches can't be applied cleanly, and someone — usually the Solutions Architect — inherits a maintenance nightmare years later, often after the original developer is long gone. Upgrade-unsafe code is debt with compound interest: cheap to write, ruinous to carry. Clean inheritance is not a style preference; it is the contract that keeps the client on supported software.

Module 7

Common development tasks

Most Odoo customization is built from a recognisable vocabulary of tasks. A fluent developer recognises which pattern a requirement calls for and reaches for the framework feature designed for it, rather than inventing machinery.

TaskHow it's done in Odoo
New modelsA Python class subclassing models.Model with _name, fields, and an entry in ir.model.access.csv — the table Odoo doesn't track natively.
Computed & related fieldscompute= methods with @api.depends (add store=True when the value must be searchable/reportable and is worth persisting); related= to surface a field from a linked record.
Constraints@api.constrains for Python validation with custom messages; _sql_constraints for database-level guarantees (unique, check) that can never be bypassed.
Onchange@api.onchange to update the form live as the user edits — UI convenience only; never the place for authoritative validation, which belongs in constraints.
WizardsTransientModel + a form view opened as a dialog: gather input, do the work, often return an action — for multi-step user operations like bulk updates or guided imports.
Automation: server actions vs PythonLow-code server/automation rules for simple "on event, do X"; a proper Python method in a module when logic is complex, tested, or version-controlled — the developer's domain.
QWeb PDF reportsA QWeb template + report action + paper format to produce branded, translatable printed documents (invoices, certificates, custom layouts).
Scheduled jobsir.cron records calling a model method on a schedule — nightly syncs, reminders, batch recomputation — written to be idempotent and batched.
External APIshttp.Controller with @http.route for inbound webhooks/endpoints; outbound calls via the requests library inside a service method, with error handling and retries.
OWL widgets / componentsJavaScript components in static/src registered via the registry, for interactive UI beyond standard views — dashboards, custom fields, client actions.
💡 Reach for the right tool

Half of good Odoo development is matching the requirement to the framework's intended pattern. A live form tweak is an onchange, not a constraint; a hard data rule is a constraint, not an onchange; a nightly task is a cron, not a controller. Fighting the framework — recreating something it already offers — is the most common way junior developers waste effort and create fragility.

Module 8

The Developer across the eight phases

The Developer is not on the project from day one to day last in the way the PM is, but they have a defined part in every phase of the Odoo lifecycle. They are consulted early for feasibility, lead the build, and are the deep-bug specialist through hypercare.

1

Initiation & kickoff

Informed, occasionally consulted. The Developer is rarely in the room at kickoff, but a senior developer or tech lead may be consulted on high-level feasibility — flagging early whether a headline goal smells like a large custom build or a heavy integration that the charter and budget must reflect.

2

Discovery & analysis

Consulted / informed. As the fit-gap surfaces genuine gaps, the Developer is consulted on technical feasibility — can this realistically be built in Odoo, and roughly how big is it? Their input keeps the FC's fit-gap honest about what "custom" will actually cost.

3

Solution design

Consulted — and the source of estimates. The SA leads the technical design; the Developer feeds it with effort estimates and feasibility, flags where a design will be expensive or fragile, and helps choose the approach that is both correct and buildable in the time available. Honest estimating here protects the whole plan.

4

Build & configuration

Leads the build. This is the Developer's primary phase. Working from the functional spec and technical design, they write the custom modules — models, views, logic, reports, integrations, OWL components — as clean, tested, upgrade-safe extensions, commit to Git, and push to odoo.sh staging where the FC configures around their work. The developer's signature output lands here.

5

Data migration

Supports. The BA owns the mapping and the FC owns load-and-validate, but the Developer builds the scripted loads — import scripts, transformation logic, and one-off migration code — for data too complex or too voluminous for the standard import framework, ensuring records land in the right models in the right order.

6

Testing & UAT

Fixes code defects. The FC leads functional testing and triages defects; the ones that are genuine code bugs come to the Developer, who reproduces, fixes, writes a regression test, and pushes. They are disciplined about distinguishing a real defect from disguised new scope, routing the latter to the PM's change control rather than quietly building it.

7

Training & go-live

Supports. The Developer is on standby at cutover — ensuring the final production deployment of custom modules goes cleanly, the migration scripts run against live data as rehearsed, and any last-minute code issue is resolved fast so the go-live runbook stays on schedule.

8

Hypercare & support

Resolves deep bugs. When hypercare surfaces an issue that isn't configuration or training but a genuine fault in custom code or an integration, it escalates to the Developer. They diagnose against the logs, fix at the root cause, add the missing test, and feed the lesson back so the same class of bug doesn't recur.

Module 9

Writing quality code

Functionality that passes UAT is the floor, not the ceiling. Quality is what makes that functionality cheap to maintain, fast at scale, and safe to upgrade — and it is judged by the SA in code review, not by whether the demo worked.

Conventions & readability

The developer follows the Odoo coding guidelines and PEP 8: consistent naming (snake_case fields, model names with dots, method naming idioms), one concern per file, clear method names, and comments only where intent isn't obvious. Code that reads like the rest of Odoo is code the next person can safely change.

Performance

  • Never query in a loop. Search once and operate on the recordset; the classic Odoo performance killer is a search or browse inside a for loop over records.
  • Use the ORM in batches — read the fields you need in one call, write to a whole recordset at once, and prefer read_group for aggregates over manual summing.
  • Mind stored computed fields — they trade write-time cost for read/search speed; store only when you must search or report on the value, and get the @api.depends exactly right or the value goes stale.
  • Index and constrain at the database where it matters, and avoid loading large recordsets into memory when a targeted search would do.

Reuse & security by default

Before building, the developer checks Odoo standard, the OCA (Odoo Community Association) modules, and TechNext's own catalog — reusing a maintained module beats writing and owning a new one. And security is designed in, not bolted on: every new model gets access rules from the start, record rules where row-level access matters, and controllers that never trust their input. A feature that leaks data is a defect even if it does what the spec said.

Module 10

Testing

Odoo ships a real testing framework, and using it is part of the developer's job, not an optional extra. Tests are how a developer proves the code meets the acceptance criteria — and how they keep it meeting them after the next change.

The Odoo testing framework

  • TransactionCase / SavepointCase — for business logic: set up records, call methods, assert the results, all rolled back after each test so the database stays clean. The backbone of testing models, constraints, and computations.
  • HttpCase + JS tours — for UI and end-to-end flows: drive the actual browser through a scripted "tour" to prove a screen, a wizard, or an OWL component behaves for a real user.
  • Tests from acceptance criteria — the developer turns each acceptance criterion in the FC's spec into an assertion, so "done" is provable, not asserted in a conversation.
  • Edge cases first — empty values, partial quantities, cancellations, permissions, multi-company: the unhappy paths where bugs actually live get explicit tests.

Tests run automatically

On odoo.sh, the test suite runs on every push to a branch: a build that fails its tests doesn't get promoted. This turns testing from a virtue into a gate — broken code is caught before it ever reaches staging, let alone UAT. The developer's habit of writing a regression test for every fixed bug compounds into a suite that protects the whole codebase across upgrades.

⚙️ The TechNext angle

At TechNext, AI drafts the first pass of tests directly from the functional spec's acceptance criteria and from the model definitions — generating the obvious happy-path and boundary cases automatically. The developer's job shifts from writing every assertion by hand to reviewing, hardening, and extending the generated tests: adding the client-specific edge cases the AI can't infer and confirming the suite actually exercises this client's logic. Faster to reach coverage; still human-verified where correctness matters.

Module 11

Working from specs & collaborating

The Developer is the receiving end of the project's most expensive handoff. Per the methodology, the FC/SA → Developer handoff is the costliest ambiguity on the project: a misread spec becomes the wrong build, discovered only at UAT, and paid for twice. How the developer handles specs and collaboration is therefore core to the role, not a soft extra.

Reading specs & asking before coding

  • Read the whole spec and design before writing a line — the business need, the exact behaviour, the data, the screens, the edge cases, and the acceptance criteria. Understand intent, not just instructions.
  • Ask clarifying questions up front — every ambiguity resolved before coding is hours of rework avoided. The expensive failure is the developer who guesses at an unclear spec and builds confidently in the wrong direction.
  • Estimate honestly — give the PM and SA a realistic effort figure, including the testing and the edge cases, not the optimistic happy-path number. A padded or under-cooked estimate poisons the plan.
  • Submit to code review — the SA (or a peer) reviews every change for correctness, convention, performance, and upgrade-safety. The developer treats review as a quality gate to welcome, not a hurdle to clear.
ℹ️ Clarify, don't assume

The single highest-leverage habit a developer has is asking the FC or SA a five-minute question instead of spending two days building an assumption. Silence in the face of an ambiguous spec is not professionalism; it is risk. The best developers make their assumptions explicit and get them confirmed before, not after, the build.

Module 13

Skills & KPIs that matter

The Developer is the most code-technical of the build roles, but the soft skills decide whether their code lands cleanly into a project. The hard skills get the build right; the soft skills get it built to spec, on estimate, and without surprises.

Hard skills

Python Odoo ORM / framework XML / QWeb JavaScript / OWL PostgreSQL / SQL Git Testing Debugging

Soft skills (the decisive ones)

Reading specs Communication Estimating Attention to detail Pragmatism Asking questions

A developer must know the framework deeply enough to extend it cleanly without fighting it — but the difference between a good developer and a costly one is rarely raw coding skill. It is whether they read the spec carefully, estimate honestly, flag blockers early, and build the boring, upgrade-safe thing instead of the clever, fragile one. Enough discipline to build to spec and stay inside the design is the bar, not maximal cleverness.

Every role has characteristic failure modes, and the Developer's are especially costly because they are usually invisible until much later — at UAT, at the next upgrade, or in the small hours of hypercare. The anti-patterns below are the ways a developer creates pain for other roles, and the guardrails that prevent each.

⚠️ Upgrade-unsafe customization is the #1 long-term harm

Of all these failure modes, the first is the one with the longest tail. A core override or a framework hack may sail through UAT and go live without a hiccup — and then, a year or two later, strand the client on an unsupported Odoo version, conflict on every upgrade attempt, and land squarely on the Solutions Architect as an un-upgradeable mess to untangle, long after the developer who wrote it has gone. Building upgrade-safe is not a style choice; it is the single biggest way a developer either protects or sabotages the client and the SA for years to come.

Module 15

Boundaries & the TechNext lean model

Knowing where the Developer stops is as important as knowing what they do.

  • Developer vs. FC: the FC specifies and configures; the Developer codes. The FC owns the business behaviour and writes the functional spec; the Developer implements it. When a developer finds themselves making business-rule decisions the spec didn't cover, that's a question for the FC, not a call to make alone.
  • Developer vs. SA: the SA designs how it's built; the Developer implements it and is reviewed by the SA. The architecture, the standards, and the upgrade-safety contract are the SA's; the clean realisation of them in code is the Developer's. The Developer pushes back when a design is impractical, but builds within it — and submits to the SA's code review.
  • Developer vs. PM: the Developer gives honest effort and feasibility input; the PM owns the schedule and the trade-off decisions. The Developer says what something will take and what a shortcut would cost; the PM decides whether it's worth it.
⚙️ How the role changes in TechNext's A-Team

In TechNext's lean, automation-first model the Developer merges into the Senior Odoo Engineer / Tech Lead seat — a single person who reads specs like an FC, respects the design like an SA, and builds, amplified by AI-assisted coding and the reusable module catalog. The boilerplate — scaffolds, obvious models, first-pass tests, repetitive view code — is increasingly drafted by AI and assembled from vetted catalog modules; repeatable custom code becomes a catalog module the moment it proves reusable. What stays irreducibly human is the design discipline: the judgment to keep it upgrade-safe, the honesty to flag a shaky estimate, and the restraint to build to spec rather than gold-plate. Automate the boilerplate; never automate the design discipline.
